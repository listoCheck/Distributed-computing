# Лабораторная №3 — скалярное время Лэмпорта

Реализация на C99 по `pa3.pdf` и требованиям `../lab2/lab2/pa2.pdf`.
Готовый архив для ручной отправки: **`pa3.tar.gz`**. Исходники находятся в `pa3/`.
Письма не отправлялись; вердикт **Passed** может дать только бот курса.

## Что реализовано

- Родитель и дочерние процессы через `fork()`, отдельный направленный pipe для каждой пары.
- Все концы каналов работают с `O_NONBLOCK`. Нет потоков, общей памяти, семафоров, `select()` или `poll()`.
- Часы начинаются с нуля. Отправка: `L = L + 1`; приём: `L = max(L, received) + 1`.
- `send_multicast()` создаёт одно событие и использует одинаковую отметку для всех получателей.
- Последовательные переводы `родитель → источник → получатель → ACK родителю`.
- Списание при отправке источником, зачисление при приёме получателем; деньги в пути учитываются на полуинтервале `[send_time, receive_time)`.
- Барьеры `STARTED`/`DONE`, корректная обработка `DONE`, пришедшего до `STOP`.
- Передача только заполненной части `BalanceHistory`, дополнение историй до общего горизонта и вызов библиотечной `print_history()`.
- Логи в `events.log`, `pipes.log` и терминал; успешный запуск возвращает 0 и не пишет в stderr.

## Дополнительные возможности

Они не добавляют сообщений в протокол и не меняют формат вывода бота:

1. **Проверка сохранения денег** перед `print_history()`: для каждого `t` сумма `balance + pending_in` равна исходной сумме.
2. **Разбор фрагментированных сообщений**: незавершённый заголовок или payload сохраняется отдельно для каждого канала; пустое чтение не двигает часы.
3. **Круговой обход входящих каналов**, чтобы постоянно активный сосед не вытеснял остальных.
4. **Проверка границ** истории, чисел и структуры сообщений; обработка `EINTR`, `EAGAIN`, EOF и ошибок создания процессов.
5. **Независимый проверяющий скрипт**: воспроизводимые случайные переводы, сопоставление каждой ячейки истории с событиями, проверки логов, запуск с ASan/UBSan.
6. **Воспроизводимая упаковка** с SHA-256 и явным списком файлов: тестовые замены, исполняемые файлы и логи не попадают в архив.

## Сборка и запуск в Linux

```sh
cd pa3
make
LD_LIBRARY_PATH=. LD_PRELOAD=./libruntime.so ./pa3 -p 3 10 20 30
```

Команда проверки из PDF с обычным ASCII-дефисом перед `L`:

```sh
clang -std=c99 -Wall -pedantic *.c -L. -lruntime
LD_LIBRARY_PATH=. LD_PRELOAD=./libruntime.so ./a.out -p 3 10 20 30
```

`-p` задаёт число **дочерних** процессов, родитель имеет ID 0. Для каждого ребёнка нужен один начальный баланс от 1 до 99. Поддерживается 1–15 детей, в условии автоматической проверки указаны 2–10.

`bank_robbery.c` — небольшой локальный сценарий: единица денег обходит счета по кольцу и возвращается. Бот заменяет этот файл своей реализацией. Основной код не зависит от кольцевого сценария.

## Проверки

В Linux с Clang и Python 3.4+:

```sh
python3 tests/verify.py --repeats 10
python3 tests/verify.py --sanitize --repeats 2
```

Тесты собирают программы во временном каталоге и не меняют `pa3/bank_robbery.c`. Проверяются 1, 2, 3, 10 и 15 детей, отсутствие переводов, нулевые суммы переводов, случайные переводы и длинные последовательности до 35 операций. Отдельный C-тест проверяет часы, multicast, частичные чтения и длинный интервал денег в пути.

Для текущей Windows-машины подготовлен локальный Docker-образ `pa3-toolchain:local`:

```powershell
docker run --rm --mount "type=bind,source=$($PWD.Path),target=/lab3" -w /lab3 pa3-toolchain:local python3 tests/verify.py --repeats 10
```

Итоги и ограничения проверки — в [docs/VALIDATION.md](docs/VALIDATION.md).

Для точной среды из PDF также подготовлен `pa3-legacy:local`. Воспроизводимая сборка и запуск:

```powershell
docker build -f tests/Dockerfile.legacy -t pa3-legacy:local .
docker run --rm --mount "type=bind,source=$($PWD.Path),target=/lab3" -w /lab3 pa3-legacy:local python3 tests/verify.py --cc clang-3.5 --repeats 10
docker run --rm --mount "type=bind,source=$($PWD.Path),target=/lab3" -w /lab3 pa3-legacy:local sh tests/check_archive.sh
```

## Ограничение формата истории

В предоставленном `banking.h` массив имеет 256 элементов, но `s_history_len` имеет тип `uint8_t`: максимальная длина — 255, то есть представимые состояния `t = 0..254`. Попытка сохранить состояние 255 требует длины 256, которая превратилась бы в 0. Программа выдаёт явную ошибку вместо переполнения. Часы сами по себе имеют тип `int16_t`; ограничение относится именно к передаваемой истории. Заголовок не изменялся.

Текстовый вывод разных процессов может перемешиваться по физическому порядку строк. Для логического полного порядка сравнивают пары `(timestamp, process_id)`; сортировка вывода во время работы не нужна и не вводит дополнительные события.
