# Лабораторная №4: взаимное исключение Лэмпорта

Задание разобрано по `pa4.pdf` (две страницы). Решение на C99 находится в `pa4/`.
За основу транспорта взяты ваши `../lab3/pa3/ipc.c`, `clock.c` и управление
процессами из `main.c`. `common.h`, `ipc.h`, `pa2345.h` и `libruntime.so`
скопированы из той же работы без изменений. `mutex.c` и `protocol.c` написаны
для этой лабораторной. Это не обещание конкретного процента антиплагиата:
общие заголовки, предыдущие работы и стандартный алгоритм неизбежно совпадают.

## Соответствие PDF

| Требование | Реализация |
| --- | --- |
| Дочерний процесс печатает `local_id * 5` раз | `child_run`, итерации с 1 |
| Использовать `print()` из библиотеки | Один вызов на итерацию |
| `--mutexl` включает взаимное исключение | `request_cs` → `print` → `release_cs` |
| Без флага нет критических секций | Нет сообщений CS и вызовов request/release |
| Алгоритм Лэмпорта | Очередь по паре `(timestamp, local_id)` и ответы всех детей |
| Пустые CS_REQUEST / CS_REPLY / CS_RELEASE | Только заголовок; отправитель определяется каналом |
| Неблокирующие read/write | O_NONBLOCK на обоих концах каждого канала |
| Скалярные часы | На отправке +1, на приёме max(local, remote)+1 |
| Барьеры STARTED и DONE | Обработка любых сообщений во время ожидания |
| Сборка C99 без предупреждений | Проверка с дополнительными `-Wextra -Werror` |
| Успех без stderr и с кодом 0 | Вывод runtime перенаправляется только на время print |

## Сборка и запуск в Linux

```sh
cd pa4
make                      # либо make CC=clang-3.5
LD_LIBRARY_PATH=. ./pa4 -p 5 --mutexl
LD_LIBRARY_PATH=. ./pa4 -p 5
LD_LIBRARY_PATH=. ./pa4 --mutexl -p 5 --trace
```

Команда бота тоже поддерживается:

```sh
clang -std=c99 -Wall -pedantic *.c -L. -lruntime
LD_LIBRARY_PATH=. ./a.out -p 5 --mutexl
```

Допустимо 1–15 детей; процесс 0 — родитель. Порядок флагов произвольный.
`events.log` содержит сообщения жизненного цикла, `pipes.log` — карту каналов.
Баланс в шаблонах STARTED/DONE равен 0: банковских операций в этой работе нет.

В имеющейся `libruntime.so` функция print вызывает `write(2, ..., 1)` и задержку
между символами. Чтобы внешний stderr оставался пустым, перед print выполняется
`dup2(stdout, stderr)`, после — восстановление исходного stderr. Функция библиотеки
не заменена и вызывается при каждой итерации. Это поведение отражено в исходниках.
Сообщения жизненного цикла не защищаются мьютексом и могут вклиниваться в вывод
итерации другого процесса; взаимное исключение относится к вызовам print.

## Дополнительные возможности

* `--trace` создаёт `mutex.trace`: `REQUEST|ENTER|EXIT id clock iteration`.
  Трасса не попадает в stdout/stderr; без флага она не создаётся.
* Декодер каждого канала сохраняет частичные заголовки и payload между чтениями.
* receive_any опрашивает отправителей циклически, не отдавая постоянный приоритет
  одному идентификатору.
* Проверяются некорректные размеры сообщений, переполнение часов, повторные
  запросы, RELEASE без REQUEST, ошибочные аргументы и ошибки дочерних процессов.

## Проверки

В Linux, после сборки, из корня проекта:

```sh
python3 tests/check.py
```

Нужен Python 3.6+. Восемь запусков: 1, 2, 5, 15 детей, с мьютексом и без.
Проверяются код завершения, пустой stderr, барьеры, число каналов, полнота вывода,
порядок итераций каждого процесса и отсутствие пересечений ENTER/EXIT.
Используется настоящая libruntime.so. В режиме без мьютекса допускается смешивание
символов, поэтому проверяется их мультимножество, а не порядок строк.
Timeout ограничивает зависшие тесты. Тесты запускаются во временных каталогах.

## Что объяснить на защите

1. Часы Лэмпорта задают причинный порядок; local_id разрешает равные timestamps.
2. У каждого процесса своя таблица заявок. При одном незавершённом запросе на
   процесс таблица эквивалентна очереди с поиском минимума за O(P).
3. Вход разрешён, если своя заявка минимальна и получен CS_REPLY от каждого
   другого ребёнка. На CS_REQUEST ответ отправляется сразу, не откладывается.
   Это алгоритм Лэмпорта, а не Рикарта–Агравалы.
4. На выходе своя заявка удаляется и всем детям рассылается CS_RELEASE.
5. Multicast получает одну временную метку: все процессы сравнивают одну и ту же
   заявку. CS-сообщения родителю не отправляются; STARTED/DONE отправляются всем.
6. DONE означает конец полезной работы, но не выход из обработки запросов.
   Каждый ребёнок отвечает другим до получения DONE от всех. Ответы нужны даже
   от уже завершивших печать детей. FIFO обеспечивает приём последнего RELEASE
   перед DONE того же отправителя.
7. Общей памяти, семафоров и файловых блокировок для взаимного исключения нет.
   Трассировка служит только наблюдению. Цена входа/выхода — 3(P−1) CS-сообщений.

Алгоритм предполагает исправные процессы и FIFO-каналы. Восстановления после
падения участника нет: остальные могут ждать его сообщения. Для штатной нагрузки
маленькие сообщения и одна заявка на процесс ограничивают заполнение каналов;
IPC не является универсальным транспортом для произвольных потоков больших данных.
